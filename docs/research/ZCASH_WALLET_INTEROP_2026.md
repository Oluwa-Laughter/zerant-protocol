# Zcash wallet interoperability review — 2026-10-05

Sources accessed 2026-10-05. This records source-level capability evidence, not a claim that every wallet build or platform was exercised with Zerant.

## No universal connection protocol

The [ZecAuth v1 draft](https://github.com/ZecHub/zechub/blob/main/Hackathon/2026/ZecAuth/PROTOCOL.md) describes the absence of a universal Zcash wallet connection standard. Its purpose-specific authentication key, signed domain/chain/nonce challenge, and callback enable portable authentication without equating a payment address with identity. It is a draft requiring wallet implementation. Zerant already implements the server verifier and browser attempt redemption; the handoff URI alone cannot authenticate a wallet that has not adopted ZecAuth.

## Transport findings

- [Noir's Zcash wallet adapter](https://github.com/NoirWallet/zcash-wallet-adapter/blob/main/README.md) describes an injected `window.noirwallet.zcash` provider, derived message-signing mode, shielded `zcash_sendTransaction`, and restoration via `zcash_getAccounts`. Zerant uses `@noir-wallet/sdk` for the verified injected provider boundary and derives the login signing key; it does not request balances or history for sign-in. The adapter's WalletStore/registry layering informed Zerant's small local connector registry; importing its optional UI and crosschain package is unnecessary for this boundary.
- [NozyWallet's repository](https://github.com/LEONINE-DAO/Nozy-wallet) and [extension README](https://github.com/LEONINE-DAO/Nozy-wallet/blob/master/browser-extension/README.md) show a developing MV3 extension, dApp prompts, and a local companion API. The reviewed extension README does not specify a stable public injected object, challenge-signing method, signing mode, or signature format compatible with Zerant's server verifier. Its desktop dApp guide is marked experimental. No Nozy identity connector is enabled until the provider contract and signature profile can be tested. A wallet-local companion HTTP API is not a browser auth protocol and Zerant does not probe localhost.
- The [Noir adapter WalletConnect section](https://github.com/NoirWallet/zcash-wallet-adapter/blob/main/README.md#-walletconnect) uses a `bip122` Zcash mainnet namespace with `zcash_getAddress`, `zcash_getBalance`, and `zcash_transfer`. Its current reference is mainnet and transparent-spend only; it does not expose message signing, shielded funding, or PCZT. A fresh Zerant WalletConnect connector advertises only connection and restoration. Transparent payment is enabled only after a verified session advertises `zcash_transfer` and a transparent account. Pairing grants no Zerant identity or shielded-payment capability. An optional project ID must be explicitly configured before any pairing; incompatible sessions must fail closed. Zerant does not ask for balance during discovery or authentication.
- [ZIP 321](https://zips.z.cash/zip-0321) defines canonical `zcash:` payment requests with recipient, amount, memo, and multiple-payment semantics. This is broad payment portability, not authentication. Zerant's native parser validates and canonicalizes the full request; the browser passes that exact URI to a compatible wallet. A direct wallet call is allowed only when every request field is representable. Wallet submission is not settlement confirmation.

## Compatibility decision

Named mobile wallets, including Zodl/Zashi, YWallet, and Unstoppable, have no verified Zerant identity-signing or ZecAuth integration from the sources reviewed here. Their ZIP-321 support is not asserted without a current wallet-specific source and exercise. Users can still copy/open Zerant's canonical URI in a wallet that supports it. A passkey gives wallet-independent account access.

New wallet adapters must bring a documented injection or transport entry point, exact request/response shapes, signing profile accepted by the server, negative capability tests, and an explicit privacy review. The connector registry can then add the adapter without changing credential, issuer, verifier, or payment-request contracts.

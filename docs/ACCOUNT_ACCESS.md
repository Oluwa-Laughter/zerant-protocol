# Zerant account access

Zerant separates **account access** from credentials, reputation, and Zcash payment authority.

## Supported access paths

### Passkeys

A user can create a Zerant account with a passkey, sign back in with that passkey, or attach additional passkeys to an existing authenticated account.

Passkey challenges are:

- generated by the Zerant service;
- stored server-side only;
- bound to one account and operation;
- valid for five minutes;
- consumed once under a database transaction;
- tied to the configured Zerant production origin through WebAuthn relying-party validation.

The browser never receives Zerant session tokens directly. Successful authentication creates the same opaque `HttpOnly`, `Secure`, `SameSite=Lax` session used by other access paths.

An account may have at most ten passkeys. Adding or removing a passkey requires a session created within the last 15 minutes. Zerant refuses to remove the last passkey if the account has no other Zcash-based authentication method, preventing accidental lockout.

### Zcash-based access

Zerant also supports purpose-specific Zcash authentication and compatible wallet-message authentication. These access methods remain separate from spending authority and generic payment addresses.

A user can add passkeys without changing the existing Zerant ID, credentials, issuer memberships, verifier profile, or Zcash configuration.

## Privacy boundary

Passkeys are an account-access mechanism only. They are not credentials, reputation signals, payment identities, or proof inputs. Zerant does not expose WebAuthn credential IDs through the customer UI or verifier APIs.

## Operational notes

The service persists serialized WebAuthn ceremony state in PostgreSQL because Vercel instances are stateless and may scale between ceremony start and finish. The stored ceremony is short-lived and one-time. The `webauthn-rs` state-serialization feature is therefore used only behind Zerant's protected database boundary.

Account settings expose only internal passkey record IDs, creation time, and last-use time. Raw WebAuthn credential material remains server-side.
